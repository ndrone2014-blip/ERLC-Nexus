# ERLC Nexus — Security

ERLC Nexus stores fictional roleplay records, but it also holds real credentials
(your Discord bot token and ERLC server key) and controls your ERLC server. This
document describes how it protects them and what you should do as an operator.

## Authentication

* **Passwordless sign-in through Discord OAuth2.** ERLC Nexus never sees or stores
  Discord passwords. The OAuth `state` parameter is signed (HMAC with `SECRET_KEY`)
  and checked on callback to prevent login CSRF.
* Scopes requested: `identify` and, when `DISCORD_GUILD_ID` is set, `guilds.members.read`
  (to read your roles in *your* server). Access tokens are used once during login and
  are not stored.
* **Sessions** are random 256-bit tokens. Only a SHA-256 hash is stored in the database.
  The cookie is `HttpOnly`, `SameSite=Lax`, and `Secure` when `COOKIE_SECURE=true`.
  Sessions expire after `SESSION_HOURS` (default 12) and can be revoked by an
  administrator on the Security page. Disabling a user revokes their sessions.
* **CSRF protection:** every state-changing API request must carry the per-session
  `X-CSRF-Token` header. Requests without it are rejected and logged.
* `DEV_LOGIN` (local first-time setup) only works when enabled in `config.env`, only from
  the same computer, only for same-origin requests, and only as `INITIAL_ADMIN_DISCORD_ID`.
  Turn it off once Discord login works. The launcher warns while it's on.

## Authorization

* Role-based access control with 40+ granular permissions (e.g. `cad.incident.create`,
  `erlc.server.moderate`, `system.configure`). See **System → Permissions**.
* **Every permission is checked on the server** in the service layer, regardless of what the
  website shows. The browser never supplies role information.
* Discord role membership comes from Discord itself — the OAuth guild-member endpoint at
  login, or the gateway when someone uses a bot command — never from the browser.
* **Least privilege by default:** new users have no permissions until a role is assigned
  or mapped from a Discord role. Only Owners can grant full access (`*`) or the Owner role,
  and the last Owner cannot be removed.
* Supervisors and command staff manage personnel only in departments where they hold a
  supervisory rank. Users cannot review their own reports or approve their own shifts.
* Interactive Discord components (buttons, menus) only respond to the user who created
  them, expire after a timeout, and re-check permissions on every click.

## Secrets

| Secret | Where it lives | Exposure |
|---|---|---|
| `DISCORD_BOT_TOKEN`, `DISCORD_CLIENT_SECRET`, `SECRET_KEY` | `config.env` (git-ignored) | Never returned by any API route or shown in the UI. |
| ERLC server key | `config.env`, or encrypted in the database (Fernet, key derived from `SECRET_KEY`) when saved from the dashboard | Write-only in the UI; never sent to browsers, Discord, or logs. |

* All log output passes through a redaction filter that masks every configured secret
  and common token patterns.
* Error responses never include stack traces or internal details; full diagnostics go to
  `data/logs/` only.
* Do not commit `config.env` or `data/` (both are in `.gitignore`). If a key leaks, rotate it
  (regenerate the bot token / ERLC server key) and update it.

## Input and output handling

* All input is validated server-side (lengths, types, allowed values, IDs).
* SQL is generated by SQLAlchemy with bound parameters — no string-built queries.
* The website builds the DOM with `textContent` only (never `innerHTML` with data); a test
  enforces this. A strict Content-Security-Policy allows scripts only from the site itself.
* Other headers: `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`,
  `Referrer-Policy: same-origin`, `Cache-Control: no-store` on API responses.
* Rate limiting: 30 login requests and 600 API requests per minute per IP.

## Audit trail

* Important actions (CAD changes, record edits, moderation, configuration, permission changes,
  logins, security events) are written to an append-only audit log with the actor, time,
  target, previous and new values.
* Each entry is **hash-chained** to the previous one. **System → Logging → Verify integrity**
  detects edited or deleted entries. There is no UI or API to modify audit entries.

## ERLC API safety

* Follows the official rate limits, waits out `Retry-After`, never rotates IPs.
* Stops all requests with a key that the API rejects (403 / codes 2000–2004) to avoid the
  documented temporary blocks and permanent IP bans.
* In-game commands are validated (must start with `:`, single line, length-limited) and
  communities can block specific commands. Every command is audited.
* Optional event-webhook endpoint verifies Ed25519 signatures with the official public key
  over the raw body and rejects anything unsigned. It is disabled by default.

## Admin security page

**System → Security** shows recent logins, active sessions (with revoke), failed
authentication attempts, permission changes and recent security events
(expired sessions, CSRF failures, denied logins).

## Operator checklist

- [ ] Keep `config.env` private; never paste tokens in Discord.
- [ ] Turn `DEV_LOGIN` off after setup.
- [ ] Leave `WEB_HOST=127.0.0.1` unless you need network access. If you expose the site
      publicly, put it behind HTTPS (see DEPLOYMENT.md) and set `COOKIE_SECURE=true` and `PUBLIC_URL`.
- [ ] Map only trusted Discord roles to powerful Nexus roles.
- [ ] Make regular backups (System → Database).

## Reporting vulnerabilities

Report security problems privately to the project maintainer. Vulnerabilities in the ERLC
API itself should be reported to PRC as described in their Acceptable Use Policy.
